Phase 1 · Plan

01

Story intake & technical grooming

JiraClaude-assisted

a business ask → a buildable, technically-groomed story

The story is the pipeline's contract, and it's the first place Claude adds value — not by writing the business ask, but by sharpening it technically. A developer or tech lead runs Claude over the draft during refinement to turn a business request into a precisely specified story before it enters the sprint. Everything downstream inherits this quality, so it's where the flow is won or lost.

What Claude does

Reads the draft story from Jira (via MCP) alongside the codebase and metadata, then drafts acceptance criteria in a consistent, parseable format, lists the objects, Apex, and LWC likely affected, flags security and governor-limit implications, proposes edge cases and a first-cut test-scenario list, and surfaces open questions to take back to the business.

Set up once

A short "groom this story" skill or prompt, plus read access to Jira and the repo. Agree a "ready" definition and story template so the groomed output lands in the same shape every time.

Watch-outs

This is technical grooming, not business authorship — a human still decides what's in scope. Claude can turn a thin story into sharp questions, but it can't invent missing product intent.

Owner · Tech lead + devEffort · Low
02

Plan

Claude Code · MCP

Jira key → a proposed plan, pending approval

The developer starts Claude Code and points it at the story key. Claude pulls the issue, its criteria, and the discussion straight from Jira over the Atlassian MCP connection, then proposes an implementation plan — the files it will touch, the approach, the tests — before editing anything.

Mechanics

Atlassian's Rovo MCP server exposes Jira to MCP clients; Claude Code connects to it through its MCP config. Plan mode produces the plan without making edits.

Set up once

Register the Atlassian MCP server in the team's Claude Code config and authenticate per developer. A short reusable prompt — read <KEY>, propose a plan — keeps it consistent.

Watch-outs

Scope the connection to read-only access and keep credentials per developer. The plan inherits the story's quality (see 01).

Owner · DeveloperEffort · Low
03

Approve plan

Human gate

proposed plan → a green-lit approach

The developer reads the plan and approves it, adjusts it, or sends it back. This is the cheapest correction point in the entire flow — catching a wrong direction here costs a minute; catching it in review costs a rewrite.

Mechanics

Interactive: the developer accepts the plan to proceed, or edits the plan text and re-runs planning until it's right.

Set up once

No tooling — a team norm that non-trivial stories always pass through plan-then-approve rather than jumping straight to code.

Watch-outs

Don't let it become a rubber stamp. Define what counts as "trivial" so skipping the gate is a consistent, deliberate call.

Owner · DeveloperEffort · Low

Phase 2 · Build

04

Development

Claude Code

approved plan → a working branch

Claude Code implements against the approved plan — editing across files, running tests, and iterating with the developer in the loop. Before pushing, an optional local "review this branch against target" pass gives the developer a pre-flight self-check.

Mechanics

Agentic editing in the working tree. The pre-flight review is a separate, fresh Claude Code invocation comparing branch to target — deliberately not the session that wrote the code.

Set up once

Make sure tests run locally. Establish the pre-flight self-review as a developer habit, not an enforced gate — enforcement lives at step 06.

Watch-outs

A session that wrote the code and then reviews itself mostly confirms its own work. Use a fresh session, and keep humans reading the diffs.

Owner · DeveloperEffort · Low
05

Create PR

Azure DevOps

working branch → an open pull request

The developer opens the PR against the target branch. This is the event that triggers the automated review — no new developer action, just the existing "open a PR" step.

Mechanics

A standard Azure DevOps PR. Your existing PR validation pipeline runs on creation and update; the review step is added into that pipeline.

Set up once

Nothing beyond wiring the review step (06) into the PR pipeline you already run.

Watch-outs

Make the review run on PR update, not just creation, so re-pushed changes are re-reviewed rather than reviewed once and forgotten.

Owner · DeveloperEffort · Low

Phase 3 · Review gate

Review gate — automated pass, then human sign-off
06

AI review

Automated

PR diff → inline review comments

On PR open or update, the pipeline sends the diff to an AI reviewer, which posts bugs, security issues, and style notes as inline comments — automatically, on every PR, whether or not anyone remembers to ask. This is the enforced version of the pre-flight check from step 04.

Mechanics — buy

Connect CodeRabbit to your Azure DevOps org. It reviews natively, comments inline, learns team preferences, and offers autofixes. Nothing to maintain.

Mechanics — build

A pipeline step pulls the diff with git, calls the Claude API with a review prompt, and posts results back through the Azure DevOps REST API. Full control; you own the upkeep.

Watch-outs

Keep it non-blocking — comments, not a hard fail, because AI review has false positives. Cap cost on large diffs. Building in-house means maintaining a mini-CodeRabbit.

Owner · Pipeline / platformEffort · Low (buy) / Medium (build)
07

Approve PR

Human gate

AI comments + diff → a merge decision

A human reviewer reads the AI's comments and the diff, then approves or requests changes. The AI made the review faster and cleared the boring findings; it did not replace the reviewer's judgment on correctness, architecture, and anything security-sensitive.

Mechanics

An Azure DevOps branch policy requires at least one human approver. The AI review is registered as an optional, informational status — not a required check.

Set up once

Branch policy on the target branch: minimum approvers, linked work items, and the review pipeline as an optional check.

Watch-outs

Never wire the AI as a required gate. For an independent read, consider running the review on a different model than the one that wrote the code.

Owner · ReviewerEffort · Low

Phase 4 · Release

08

Merge to non-prod

Auto deploy

approved PR → change live on non-prod

On merge, your existing CI validates and deploys to the non-prod target; the change then waits in the sprint package. This is your current path, untouched — the AI additions sit before this step, not inside your deploy pipeline.

Mechanics

The merge → build → deploy-to-non-prod pipeline you run today, unchanged.

Set up once

Nothing new.

Watch-outs

Keeping this step untouched is the point — the proposal adds no risk to how you already ship to environments.

Owner · PipelineEffort · None
09

Sprint release

Production

merged changes → one released package

All ready changes ship to production as a single package on the weekly or bi-weekly cadence. The release event doubles as the documentation checkpoint: it's what triggers the consolidation described below.

Mechanics

Your existing release pipeline, plus a hook that gathers the PRs and stories in the package and kicks off doc drafting.

Set up once

A release-time job that collects what's in the package and starts the doc consolidation run.

Watch-outs

Keep doc generation off the critical deploy path — it runs alongside the release, and a doc failure must never block a production deploy.

Owner · Release lead / pipelineEffort · Medium

Parallel · Testing

AI-assisted testing

Separate from the unit tests written during build, AI earns its place in the testing that's expensive to maintain by hand. This sits across non-prod validation (step 08) and the pre-release gate (before step 09): Claude authors, maintains, and triages the tests and data; the pipeline executes them.

Test data & scenarios

Claude generates realistic, referentially-consistent Salesforce datasets for a given scenario — Accounts, Contacts, and Opportunities that actually hang together — to seed a sandbox for automated or manual testing. It authors the recipes; the CLI loads them.

Snowfakery recipes · sf data tree
synthetic only — never prod PII

Regression testing

For each change, Claude helps pick which regression scenarios are in scope (impact-based selection), keeps the suite current as the app evolves, and triages failures with root-cause summaries and flaky-test detection — turning a red run into a short, actionable list.

existing suite · CI on non-prod

Front-end & API execution

Claude generates and maintains end-to-end UI and API tests and runs them against non-prod — browser flows through a test framework, and API / integration checks against endpoints. For exploratory runs it can drive the browser directly.

Playwright / UTAM / Provar
Postman + newman · Claude in Chrome

Claude's role is authoring, maintaining, and triaging — the pipeline is the test runner, and a human still owns the go / no-go at release. Most of these tools are open-source (Snowfakery, Playwright, UTAM); Provar is a commercial Salesforce option if you want low-code test maintenance, and can be added to the licensing table if it's in scope.

Parallel · Documentation

Documentation track

This is the part to be most clear-eyed about, because "docs stay updated automatically" is realistic for one kind of documentation and aspirational for the other. Separating the two is what makes it work.

Change history

Release notes and "what changed this sprint." Append-only, so the AI can aggregate the package's PRs and stories into a draft with little friction.

Automatable — high value

Living reference

"How the pricing engine works today." Has to be edited in place; an AI that only appends makes it longer and eventually wrong. Needs a human owner per page.

Human-owned — assisted

Cadence — tied to release, not to every PR

Mid-sprint PRs are partial and often superseded, so per-PR publishing is noise. Each PR only produces a draft doc fragment as part of Definition of Done — which is what stops it being skipped — and those fragments are consolidated at the sprint release.

Layered page — one page, two audiences

A plain-language "what this does and why it matters" summary sits on top; technical detail sits below or on a child page. The AI drafts the business layer well from a diff; engineers own the technical layer. Trying to serve both audiences in one undifferentiated block satisfies neither.

Prerequisite — a feature-to-page map

The consolidation job needs to know which Confluence page owns which feature or module, or auto-updates scatter. Maintain that mapping so a change's docs land in the right place.

Mechanism

Either Rovo inside Confluence, or a release-time job that feeds the merged PRs and stories to Claude and posts drafts via the Confluence REST API. Either way, a person reviews before publish — a wrong page read as authoritative erodes trust faster than a missing one.

Standards & guardrails

How the agent stays on the rails

Consistent quality from an AI-driven pipeline comes from three layers working together — and the rules that truly cannot slip live in the deterministic one, not in a document the model reads and mostly follows.

Layer 1 · Guidance

CLAUDE.md

A project standard checked into the repo and read at the start of every session — stack, enterprise patterns, naming, security musts, build commands. It guides the agent; it does not enforce.

Layer 2 · Procedures

Skills

On-demand recipes for recurring work — scaffolding an fflib service, an LWC, a trigger, or running a security review — so enterprise patterns are applied consistently instead of remembered.

Layer 3 · Enforcement

Hooks + CI

Deterministic gates that run every time and can block — linters and static analysis on edit, coverage gates in CI, and the org-access guard below. This is where "must" becomes binding.

Org-access guardrail

A pre-execution hook inspects every Salesforce CLI command before it runs, resolves its target org against an allowlist, and applies a fixed policy — failing closed on anything it can't classify or that names no explicit target.

Org Read Write
devuk — personal sandbox allow allow
uat ask — approval deny
prod deny deny
unknown / no target named deny deny

The strongest guarantee is that production is never authenticated in this environment — prod deploys run only from the release pipeline with their own approvals. For a team, the hook is deployed through enterprise managed settings so a developer's local config cannot remove it.

The limit worth agreeing up front

Seat prices are predictable; the usage underneath them is not. Claude Code Premium seats, CodeRabbit, and any API path all meter actual work, so a few heavy users can run ahead of the flat seat cost. The mitigations are built in: set org-level budget caps in the Anthropic console before rollout, lean on CodeRabbit's "only PR-creators are billed" model to keep the reviewer count honest, and — on the build path — use the API key's hard spend ceiling. Agree a per-seat floor plus a capped usage ceiling with the client so there are no surprises on the invoice.

Appendix · the deeper-dive questions

What comes up when this gets real

Data & IP handling

The questions a client asks first:

  • Claude Code does not train on your content by default.
  • CodeRabbit retains code only briefly for the review, then discards it.
  • MCP credentials stay per developer and read-only.
  • Flag anything client-sensitive before it reaches a third-party reviewer.

How we'll know it worked

Measure on the pilot squad, before and after:

  • PR cycle time — open to merge.
  • Defects caught before non-prod.
  • AI comments resolved before the human review starts.
  • Documentation freshness at each release.

How we'd roll it out

A 4–6 week pilot on one squad: Claude Code for the build, an AI reviewer on the Azure PRs, and Rovo for stories and docs. Prove the two high-value integration points — build and review — measure them, then decide whether the test-generation and Atlassian-agent layers are worth adding before rolling wider.

What has to be in place first

  • A Jira "ready" definition and story template.
  • Atlassian MCP access for Claude Code.
  • Claude Code seats provisioned.
  • Azure DevOps branch policies on target branches.
  • A review step in the PR pipeline.
  • A Confluence feature-to-page map.
